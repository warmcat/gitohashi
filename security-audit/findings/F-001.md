# F-001 — shutdown-order UAF: jg2 vhost freed while threadpool workers still use it

## Location

- Flawed ordering: `src/protocol_gitohashi.c:453-462`
  (`LWS_CALLBACK_PROTOCOL_DESTROY`):
  `jg2_vhost_destroy()` → `lws_threadpool_finish()` → `lws_threadpool_destroy()`
- Freed state: `lib/main.c:437-520` (`jg2_vhost_destroy`: `git_repository_free`
  per repo, `git_libgit2_shutdown`, `free(vhost)`)
- Used-after-free: `lib/job/job.c:140-364` (`jg2_ctx_fill` dereferences
  `ctx->vhost->cfg.md5_*` function pointers, `ctx->vhost->repodir`,
  `vhost->lock`, `cachedir` throughout) and `lib/main.c:884-892`
  (`jg2_ctx_destroy` locks `ctx->vhost->lock`)

## Build gating

None — default daemon build (protocol_gitohashi.c is compiled in statically
via `src/main.c`).  The window opens at daemon/vhost teardown.

## Attack path

1. A threadpool worker is inside `task_function` → `jg2_ctx_fill(priv->ctx,
   ...)`, e.g. an expensive git blame on a large file in a public repo —
   unauthenticated clients can start these at will and the blame-shed logic
   (02df748) deliberately lets them run while the pool can still make
   progress.
2. The daemon is stopped/restarted (systemd) or, in the
   `GOH_LWS_PLUGINS=ON` plugin dimension, the hosting application destroys
   the vhost.  lws closes all wsi first (task is told STOPPING, but a worker
   *currently executing* the fill keeps running until it returns), then
   delivers PROTOCOL_DESTROY.
3. `jg2_vhost_destroy` runs before any threadpool call: frees every
   `git_repository`, calls `git_libgit2_shutdown()` underneath active
   libgit2 users, destroys `vhost->lock`, `free(vhost)`.
4. The still-running worker's fill path dereferences the freed vhost
   (function-pointer calls through `ctx->vhost->cfg.md5_*`, mutex lock on
   destroyed `vhost->lock`, `repodir`/`cachedir` walks) — heap UAF.
5. Afterwards, `lws_threadpool_destroy` joins the workers and runs the
   done-queue cleanups (`cleanup_task_private_data` → `jg2_ctx_destroy` →
   `pthread_mutex_lock(&vh->lock)` on freed memory) — a second UAF leg.

## Evidence

```c
/* src/protocol_gitohashi.c, LWS_CALLBACK_PROTOCOL_DESTROY */
jg2_vhost_destroy(vhd->jg2_vhost);
lws_threadpool_finish(vhd->tp);      /* marks destroying; does NOT wait  */
lws_threadpool_destroy(vhd->tp);     /* joins workers + reaps cleanups —
                                        too late: vhost already freed    */
```

`lWS_THREADPOOL` semantics verified in lws threadpool.c: `finish` only marks
`destroying` and STOPPED-moves the pending queue (threadpool.c:796-824);
`destroy` does the `pthread_join`s and then the done-queue cleanups
(threadpool.c:865-881).  lws context destroy closes wsis before delivering
PROTOCOL_DESTROY (lib/core/context.c destroy sequence), so live wsis do not
protect the vhost — only joined workers could, and they are joined last.

## Impact

UAF-class memory corruption confined to the shutdown window of an exiting
process: crash / unclean stop under systemd, plus libgit2 global-state
teardown under active users.  No confidentiality/integrity impact shown;
aiming the corruption inside the window is contrived.  Low severity, high
confidence in the race existing.

## Remediation sketch

In `LWS_CALLBACK_PROTOCOL_DESTROY`, reverse the order: run
`lws_threadpool_finish(vhd->tp)` + `lws_threadpool_destroy(vhd->tp)` first —
destroy joins all workers and reaps every done task (each task cleanup
destroys its `jg2_ctx` while the vhost is still valid) — and only then call
`jg2_vhost_destroy(vhd->jg2_vhost)`.

- 2026-09-06 — filed open by SA-001 (proto-gitohashi pass).
- 2026-09-06 — **fixed** in `0669f37` ("threadpool: destroy pool before
  jg2 vhost at PROTOCOL_DESTROY, fixes F-001").  Exactly the recommended
  shape: `lws_threadpool_finish()` + `lws_threadpool_destroy()` (which
  joins the workers and reaps the done-queue tasks, each cleanup destroying

  `jg2_vhost_destroy()`, plus a comment stating the ordering constraint.
  En-route verification: lws threadpool worker loop re-read — after
  `finish` sets `destroying`, workers re-entering `task_function` are
  handed STOPPING and exit promptly, and a SYNC return with a detached wsi
  is bypassed rather than parked, so the joins in `destroy` cannot
  deadlock; only a worker already inside the fill runs on, which is
  precisely the case the reorder protects.  Compile-verified (incremental
  `gitohashi` target, -Werror); no runtime fence added — the repo has no
  test harness infrastructure, and the race needs a daemon shutdown with
  an in-flight blame to exercise.
