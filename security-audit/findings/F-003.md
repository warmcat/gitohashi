# F-003 — unbounded avatar cache growth (count and size) + outbound fetch amplification

## Location

- Uncapped body writes: `src/protocol_avatar-proxy.c:427-433`
  (`write(req->fd, in, len)` in `LWS_CALLBACK_RECEIVE_CLIENT_HTTP_READ`)
- Permanent entry per distinct md5: `:261-276` (`mention()` queues),
  `:467-474` (`COMPLETED` renames temp to the final cache name, no status
  check)
- No reaping/budgeting anywhere in the unit (contrast the JSON cache's
  `cache-size-limit` pvo + `lws_diskcache` LRU on the gitohashi protocol)

## Build gating

Default build, default example vhost (`/git/avatar` mount,
`origin: callback://avatar-proxy` in `etc-gitohashi/conf.d/localhost`).
Leg 1 additionally needs push access to any served repo; leg 2 needs a
malicious/compromised avatar provider, or an `http://` remote-base (SSL is
only requested for `https` schemes, :113-114).

## Attack path

**Leg 1 — repo pusher (count growth + outbound amplification):**

1. Pusher commits (or imports history) with N synthetic
   `Author: <random>@x` identities — emails are fully pusher-controlled.
2. Anyone (including the pusher) views a page that renders those
   identities; jg2 computes md5 per email and calls the avatar cb
   (`lib/email/email.c:69/:140`) → `mention()` on a worker thread.
3. `mention()` dedupes per md5 and per in-flight request, but every
   *distinct* md5 enqueues one outbound GET to the provider and, on
   success, one permanent file `cache-dir/<c>/<c>/<md5>_avatar`.
4. Nothing ever bounds the file count or total bytes; there is no LRU, no
   ttl sweep, no quota.  N is chosen by the pusher.

**Leg 2 — provider/MITM (per-file size):**

1. The provider (or a MITM if remote-base is `http://`) controls the
   response body.
2. `RECEIVE_CLIENT_HTTP_READ` streams it verbatim into the temp file —
   no size cap, no content-type check, no status check (a 404/500 page
   becomes the cached avatar for that md5 permanently).
3. An arbitrarily large body fills the disk holding the cache dir; the
   subsequent `write()` failure takes the `nope` path, which additionally
   leaks the temp (F-004), compounding the pressure.

## Evidence

```c
/* RECEIVE_CLIENT_HTTP_READ — provider body straight to disk, uncapped */
req = (struct req *)user;
if (req && write(req->fd, in, len) != (ssize_t)len)
        goto nope;

/* COMPLETED — whatever arrived becomes the permanent cache entry */
if (req && req->fd != -1) {
        if (rename(req->filepath_temp, req->filepath))
                return 0;
}
```

No size check, no status check, no total-budget check anywhere between
them.

## Impact

Disk exhaustion of the gitohashi host (repos and the JSON cache share the
consequence), plus outbound-request amplification against the avatar
provider from the gitohashi origin.  Gated on the repo-pusher or
provider positions rather than the raw anonymous client → Medium.
Medium confidence: the absence of any cap is code-verified; leg-1 velocity
depends on provider response sizes (slow-grow against a well-behaved
provider, unbounded over time), leg 2 is immediate for a hostile provider.

## Remediation sketch

- Cap the streamed body (fail + unlink temp past e.g. 1 MiB).
- Check the response status before `rename()`; don't cache non-2xx.
- Add a count/byte budget for the cache dir with oldest-first eviction
  (the JSON cache's diskcache demonstrates the pattern in this codebase).
- Consider refusing non-`https` remote-bases at INIT.

## Status history

- 2026-09-06 — filed open by SA-002 (avatar-proxy pass).
- 2026-09-06 — impact nuance recorded by SA-003: in the **shared-dir**
  deployment shape (the shipped example points `cache-dir` and
  `cache-base` at the same directory — see F-007), lws_diskcache_trim
  counts every regular file under `<c>/<c>/` toward the JSON cache's
  `cache-size` budget and LRU-trims them, so avatar files are disk-bounded
  by the JSON cache limit in that shape.  However (a) a separate avatar
  `cache-dir` remains fully unbounded, (b) the uncapped single-body write
  leg is unaffected (one huge provider body outruns the 256s-spread trim
  cadence), and (c) trim-evicted `_avatar` files are re-fetched on the
  next `mention()` — the outbound-amplification leg becomes an unbounded
  re-fetch cycle under the shared-dir shape too.  Finding stays open.
- 2026-09-13 — fixed (07894a8): provider bodies capped at 1MiB per fetch, only 2xx responses cached, and the cache dir managed by lws_diskcache (dir prepared at INIT, byte budget via optional cache-size pvo, oldest-first trim from a 1s sul) so both file count and total bytes are bounded even in a dedicated avatar cache dir.
- 2026-09-13 — audit-verified by SA-005 (Track A fix-delta pass): 1MiB cap checked via req->got before the write (no overflow), non-2xx rejected at ESTABLISHED_CLIENT_HTTP, byte budget + 1s trim sul + lws_diskcache_prepare 0700, destroy cancels sul + destroys dcs with NULL guard. Residuals accepted + recorded: one-fetch-per-distinct-md5 outbound rate stays uncapped (by-design dedupe-and-cache), http:// remote-bases remain permitted (body-capped + 2xx-gated, so a MITM's impact is avatar content only).
