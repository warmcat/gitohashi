# F-004 — wrong-path unlink + missing temp cleanup leaks a file per failed fetch

## Location

- Wrong unlink: `src/protocol_avatar-proxy.c:487-495` (`nope:` label —
  `(void)unlink(req->filepath);`)
- Temp lifecycle: created `:93-101` (`r->filepath_temp`), renamed to
  `req->filepath` only at `:467-474` (`COMPLETED`)
- Missing cleanup: `LWS_CALLBACK_CLIENT_HTTP_DROP_PROTOCOL` `:449-465`
  closes fd, dll2-removes and frees the req but never unlinks the temp

## Build gating

None — default build; triggered by any mid-body fetch failure (provider
reset, `write()` short/error e.g. under disk pressure, failed
`lws_http_client_read`).

## Attack path

1. Avatar fetch starts: temp file `<final>~<pid>-<vhd>` created
   (`O_TRUNC|O_CREAT`, 0600).
2. Body transfer fails partway → `goto nope`.
3. `nope:` unlinks `req->filepath` — the **final** name, which does not
   exist yet (rename happens only at COMPLETED) — so the unlink is a
   no-op against a nonexistent path.
4. `return -1` closes the client connection → `DROP_PROTOCOL` runs the
   cleanup: `close(req->fd)`, dll2 remove, `free(req)` — no unlink.
5. The partial temp file remains on disk forever.  The `rename()`-failure
   leg at `:471-472` (`return 0` with the temp still present) leaks the
   same way.

## Evidence

```c
nope:
	if (req && req->fd != -1)
		(void)unlink(req->filepath);   /* only filepath_temp exists here */
```

## Impact

One leaked partial file per failed fetch attempt, in the avatar cache dir
which has no sweeper (F-003 documents the missing budgeting).  Failed md5s
are re-queued by later mentions, so a persistently failing identity leaks
repeatedly; self-amplifying under disk pressure (write fails → leak →
less disk).  Low severity (slow disk litter, no memory corruption), high
confidence (wrong-variable bug, flow-verified).

## Remediation sketch

Unlink `req->filepath_temp` in `nope:` and on the rename-failure leg —
or track a "renamed" flag on the req and unlink the temp centrally in
DROP_PROTOCOL when it was not yet renamed.
