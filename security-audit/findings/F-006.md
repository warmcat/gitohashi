# F-006 — stack overflow in cache_write_complete with long (accepted) cache-base paths

## Location

- Flawed copy: `lib/job/job.c:483-513` — `char final_name[128]` (:485) and
  `memcpy(final_name, ctx->cache, n)` (:508) where `n` = offset of `~` in
  the cache path
- Accepted input domain: `JG2_CACHE_BASE_MAX` = 256 (`lib/private.h:76`),
  enforced at `lib/main.c:286` — bases up to 256 chars are *supported*
- Correctly-sized sibling: `ctx->cache[384]` (`lib/private.h`), sized by the
  same fence comment for base + 71 bytes of structure

## Build gating

Default build; requires a vhost `"cache-base"` pvo longer than 91 chars —
unusual but explicitly within the supported range (the 256-char fence
exists to make such bases work correctly, per its own comment).

## Attack path

1. Operator configures `"cache-base": "<250 chars>"` — accepted
   (`strlen ≤ 256` passes the fence).
2. First non-bot cacheable request → `lws_diskcache_query` materializes
   the temp path in `ctx->cache`:
   `<250>/<c>/<c>/<32hex>~<pid>-<ptr>` (≈308 bytes, fits `ctx->cache[384]`).
3. Job completes → `meta_trailer` → `cache_write_complete`:
   `n = strchr('~') - ctx->cache` = 250 + 5 + 32 = **287**.
4. `memcpy(final_name, ctx->cache, 287)` writes **159 bytes past
   `final_name[128]`** — a stack buffer in `cache_write_complete`
   (worker-thread frame) → return-address class corruption; the subsequent
   `rename()` also operates on the smashed (unterminated) buffer.

## Evidence

The fence comment (private.h:66-76) computes the worst-case on-disk
structure overhead (71 bytes) and sizes `ctx->cache` for base ≤ 256 —
`final_name` was simply never given the same treatment.

## Impact

Memory corruption in the worker thread on the first cache finalize, driven
by operator config inside the accepted domain.  Operator-gated (not
remotely triggerable) → Medium; high confidence (pure size arithmetic,
code-verified).

## Remediation sketch

Declare `final_name[sizeof(ctx->cache)]` (or clamp `n` to
`sizeof(final_name) - 1` and skip the rename if it would not fit).

## Status history

- 2026-09-06 — filed open by SA-003 (job-core pass).
- 2026-09-13 — fixed (10f873e): final_name declared sizeof(ctx->cache) so every cache base accepted by the JG2_CACHE_BASE_MAX fence fits; verified at runtime with a 102-char cache-base (finalize + rename complete cleanly).
- 2026-09-13 — audit-verified by SA-005 (Track A fix-delta pass): final_name[sizeof(ctx->cache)] closes the accepted-domain overflow; no other consumer of the 128-byte bound exists.
