# F-007 — avatar mount exposes the shared JSON cache; cross-vhost ACL bypass

## Location

- Config shape: `etc-gitohashi/conf.d/localhost:119,136` and
  `conf.d/unixskt` — `"cache-base": "/var/cache/libjsongit2"` (gitohashi
  protocol) **and** `"cache-dir": "/var/cache/libjsongit2"`
  (avatar-proxy) — the same directory
- Serving side: `src/protocol_avatar-proxy.c:362-387` — the mount opens
  `<cache-dir>/<p[0]>/<p[1]>/<tail>` for any unauthenticated request whose
  tail has no '/' and no '..'
- Key layout: `lib/job/job.c:157-296` (unsalted, vhost-independent key for
  repo-affiliated jobs) + lws `lws_diskcache_query` on-disk shape
  `<base>/<h[0]>/<h[1]>/<name>` (diskcache.c:188-189)

## Build gating

Default build; the shipped example conf for both vhosts.  Exploitation
needs per-vhost ACL differentiation across vhosts sharing the dir — the
deployment the conf comments themselves recommend ("The recommended
convention is a virtual user 'v-vhostname' in gitolite config and here").

## Attack path

1. Deployment: vhost A (`acl-user "@all"`) and vhost B (`acl-user
   "v-members"`) over the same repo-base-dir (repodirs are deduped by
   path) and the same shared cache dir.  Repo `x` is readable on A,
   private on B.
2. The cache key for `x`'s views is
   `md5(job+epoch ‖ count ‖ search ‖ repo-refs-md5 ‖ repo_path ‖ mode ‖
   path ‖ oid ‖ repo-conf)` — every input is a property of the **repo and
   the request**, none of the vhost.  A view of `x` rendered via A
   (public) and one rendered via B (members-only) produce the *same*
   cache file.
3. Attacker computes the key from A (all inputs public there), or simply
   reads the `"cid"` field of any response they can already see.
4. `GET /git/avatar/<32hex-name>` on **either** vhost (the avatar mount
   has no ACL) → avatar-proxy opens `<shared>/<h0>/<h1>/<32hex>` →
   `lws_serve_http_file` returns the cached private-repo JSON
   (`Content-Type: image/png`).  Names carrying `-suffix` pass the mount
   guard as well.

## Evidence

`lws_diskcache_query`'s path (`%s/%c/%c/%s`, base + first two hash chars +
full name) is shape-identical to the avatar mount's serving path — the
only thing keeping the two populations apart is the `_avatar` name suffix
of avatar files, which the mount does not require.

## Impact

Confidentiality bypass of vhost-level repo ACLs: private-repo views (file
trees, log metadata, descriptions) disclosed to unauthenticated clients.
Gated on the mixed-ACL + shared-dir config shape rather than the
single-vhost default (both example vhosts ship `@all`, and single-vhost
cache content is already public) → Medium; medium confidence (code path
fully verified, exploit needs the documented-convention deployment).

## Remediation sketch

- Give the avatar cache its own directory in the example conf and document
  that it must not equal the JSON `cache-base`; and/or
- restrict the avatar mount to tails ending in `_avatar` (the only names
  it creates); and/or
- hash a vhost identity into repo-affiliated cache keys so cross-vhost key
  equality cannot happen.

## Status history

- 2026-09-06 — filed open by SA-003 (daemon-boot pass; flaw spans
  avatar-proxy serving + cache key design).
- 2026-09-13 — fixed (2d61554): both example confs give the avatar cache its own dir (documented as must-not-equal cache-base; structure auto-prepared at avatar-proxy INIT), and the avatar mount only accepts the exact <32hex>_avatar filename shape it creates, so JSON cache entries are not servable through the mount even under dir misconfiguration.  The third sketch option (vhost identity salted into repo-affiliated cache keys) was not taken: it invalidates every existing cache entry for all deployers.
- 2026-09-13 — audit-verified by SA-005 (Track A fix-delta pass): confs split the dirs with explanatory comments AND the mount is fenced to the exact ^[0-9a-f]{32}_avatar$ shape (length 39, lowercase hex, suffix) — the fence also protects legacy/misconfigured shared-dir deployments since JSON cache names cannot match. The unsalted vhost-independent key leg remains as future hardening (hashing a vhost identity into repo-affiliated keys); the exposure route is closed.
