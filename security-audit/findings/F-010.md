# F-010 — uninterruptible full-repo index builds exhaust the worker pool

## Location

- Extent walk: `lib/job/search.c:405-507`; index walk: `:683-816` — both
  `do { … } while (1)` with no buffer/yield checks
- STOPPING is only observable at `task_function` entry
  (src/protocol_gitohashi.c:95); `ctx->outlive` detaches from the wsi but
  not from the worker
- The 503 shed (02df748) keys on `strstr(priv->url, "/blame")` only

## Build gating

Default build; impact scales with hosted repo sizes.

## Attack path

1. Repo's current refs state has no cached trie (fresh push, or never
   searched).
2. Unauthenticated `GET /git/<repo>/search/<needle>` (or a view that
   chains the search job after tree) reaches `job_search_start` →
   CREATING → the worker executes two complete tree walks plus a
   full-text index of every whitelisted file **in one call**.
3. Attacker does this for the largest unindexed repos → all 4 workers
   enter uninterruptible index builds; the queue (depth 12) absorbs and
   then rejects everything else — all gitohashi views stall, not just
   search.
4. Refs changes re-trigger new tries (each push → new refs hash → new
   index); the `ongoing` dedup only collapses concurrent identical builds.

## Evidence

No `JG2_HAS_SPACE` / partway logic inside either loop — contrast
snapshot.c's walk which yields on buffer state and streams blobs across
calls.

## Impact

Unauth-triggerable whole-service stall, gated on large hosted repos
(kernel-scale → minutes per index; first-touch forcing of every hosted
repo's index is an availability lever).  Medium, medium confidence
(mechanism code-verified; duration depends on hosted content).

## Remediation sketch

Yield inside the index walk every N entries (set `partway`, return 0, as
snapshot's blob streaming does), and/or extend the shed heuristic to
search-mode URLs when the pool is saturated.
