# F-014 — unpurified trie strings into JSON

## Location

- ac loop: `lib/job/search.c:611-627` —
  `CTX_BUF_APPEND("%c\n{ \"ac\": \"%s\", …", …, ((char *)(ctx->ac + 1)), …)`
  (autocomplete tokens come from indexed file *contents*)
- fp loop: `:647-671` — `((char *)(ctx->fp + 1)) + ctx->fp->matches_length`
  (file *paths* — repo-controlled tree entry names)

Both raw `%s` into the JSON, no `jg2_json_purify`/`ellipsis_purify`.

## Build gating

Default build; render-time impact fenced by the strict CSP
(`script-src 'self'`, no unsafe-inline) to markup/JSON-structure
injection — same class and grading as F-008.

## Attack path

1. Repo pusher commits whitelisted files (`*.c`, `README`, `*.md`, …)
   whose names or contents contain `"`, backslash or control characters.
2. The names/tokens are indexed into the search trie verbatim.
3. Any client's search/autocomplete/filepath request returns them raw
   into the JSON — `{"fp": "a", "evil": "", …}` — injected members are
   consumed by jg2.js at its DOM sinks (markup injection inside the page;
   active script fenced by CSP).

## Evidence

Every other repo-derived emission in the job family goes through
`ellipsis_purify`/`jg2_json_purify`; these two loops are the gap.

## Impact

JSON structure + CSP-fenced markup injection from repo content, served to
every user who searches.  Low, high confidence the interpolation is
unpurified.

## Remediation sketch

Purify both strings (`ellipsis_purify` into a scratch buffer as
meta_header does) before the `%s`.

## Status history

- 2026-09-06 — filed open by SA-004 (job-search pass).
- 2026-09-13 — fixed (cdc08c6): both ac and fp strings routed through ellipsis_purify(); verified at runtime with a repo file named weird"name.c whose fp result renders as weird\u0022name.c.
- 2026-09-13 — audit-verified by SA-005 (Track A fix-delta pass): both loops purify into stack scratch (256/512) via ellipsis_purify; HTML_SAFE escaping verified under F-008 — repo-controlled tokens and paths can no longer shape JSON.
