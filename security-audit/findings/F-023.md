# F-023 — one-shot 60s sul never re-armed caps threadpool responses

## Location

- `src/protocol_gitohashi.c:735` — `lws_set_timeout(wsi,
  PENDING_TIMEOUT_THREADPOOL_TASK, 60)` armed once after `http_reply`;
  the chunk-write path (:748-762) never re-arms it
- lws semantics: `__lws_set_timeout` (lib/core-net/wsi-timeout.c:240-253)
  inserts `wsi->sul_timeout` as a **one-shot**; the callback closes the
  wsi when it fires; only an explicit `lws_set_timeout()` re-inserts it
  (no role/TX path refreshes it on progress)

## Build gating

None — default build.

## Attack path

1. Unauthenticated request for a view whose generation + streaming
   exceeds 60s wall clock (huge blame, giant tree/plain listing, slow
   cache read) — headers sent, timer armed.
2. The sul fires at 60s → wsi closed mid-body → the task observes
   STOPPING at its next slice boundary and aborts cleanly (no hang, no
   pool jam — the F-010 slice discipline holds).
3. Index-build leg: the build-then-answer flow (29a5557) ties trie
   completion to the requesting wsi — builds >60s abort, leave one
   `~temp` in the cache dir, and fully retry on the next request: the
   repo stays unsearchable forever (the pre-fix outlive flow could
   complete such builds).  Disk stays bounded (the diskcache trim
   counts the temps); the waste is worker time (shed-bounded).

## Evidence

Single arming site vs one-shot sul semantics, both code-verified
(grep-level on protocol_gitohashi.c + read of wsi-timeout.c's insert
path and the absence of any implicit refresh).

## Impact

Availability/functional truncation, content/size-gated; no memory
safety or pool-liveness impact.  Low, medium confidence on real-world
frequency (mechanism certain; how often >60s views occur depends on
hosted content).

## Remediation sketch

Re-arm the timeout after each successful chunk write (converting the
cap into a 60s-inactivity bound for streaming views); for the search
index-build phase, arm a larger explicit budget or decouple trie
completion from the requesting wsi (completion marker picked up by the
next requester).
