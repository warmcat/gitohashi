# F-024 — unbounded markdown recursion → stack exhaustion

## Location

- `lib/job/markdown.c:619-647` — blockquote branch: strips one `>` per
  line and recurses into `md_lines(m, inner, ic)` with no depth
  accounting
- `lib/job/markdown.c:353-381` — nested `**`/`*` recurse into
  `md_inline` with no cap (same class)

## Build gating

None — the markdown path is the default README view and blog rendering.

## Attack path

1. Repo pusher commits a README (or blog article) whose content is one
   long line of `>` characters (or deeply nested emphasis constructs).
2. `jg2_markdown` splits into lines (2048-line cap does not help — a
   single line suffices) and calls `md_lines`.
3. The blockquote branch consumes ONE `>` and recurses on the
   remainder: recursion depth = the number of leading `>` in that line,
   bounded only by blob size (≤ the 32 MiB capture).
4. Stack exhaustion → worker SIGSEGV; the failed render is not cached,
   so every subsequent view re-crashes.

## Evidence

No depth parameter exists anywhere in the recursion chain; the inner
line array cap (128) bounds lines per level, not levels.

## Impact

Repo-content-gated, unauth-detonated service DoS — a crash per view,
harder-lived than F-016's memory pressure.  Medium, high confidence
(mechanism code-verified; trivially constructible input).

## Remediation sketch

Thread a depth counter through `md_lines`/`md_inline`, bailing to
literal escaped text past ~16 levels (real content never nests that
deep).

## Status history

- 2026-09-18 — filed open by SA-016 (job-ssr pass).

- 2026-09-18 — **fixed** by retiring lib/job/markdown.c for the lws
  streaming markdown renderer (lws-md): blockquotes are a fixed-depth
  container stack capped at LMD_NEST_MAX (24) with deeper markers
  rendering literally, and inline nesting is capped at 32 with literal
  fallback; the class is covered by test-md deep-nesting and hostile
  rounds in the lws tree.
