# F-027 — indented-code blank line strips a fixed 4 from a shorter length

## Location

- `lib/job/markdown.c:802-815` — the indented-code loop accepts blank or
  ≥4-space-indented lines, then computes
  `cs = lines[n].s + (ci > 4 ? ci : 4); cl = lines[n].len - (ci > 4 ? ci : 4)`
  where `ci` is the leading-space count (0 for a blank line)

## Build gating

None — default build.

## Attack path

1. A markdown document containing an indented code block with an
   interior blank (or 1-3 char) line — extremely common in real readmes:
   any 4-space-indented block with a separating empty line.
2. For `len < 4`, `cl = len - 4` wraps to ~SIZE_MAX and `cs` points four
   bytes past the line start (into the following markdown content or
   past the end of the staged blob).
3. `md_esc()` then loops over ~SIZE_MAX bytes appending each to the
   output hbuf (escaping only `& < > "`) — copying the remainder of the
   markdown buffer and then heap beyond it into the rendered, cached,
   publicly-served HTML until it happens to stop on an allocation
   failure.

## Evidence

Code-verified arithmetic on the staging path; the loop condition
`is_blank(...) || ind(...) >= 4` admits zero-length lines for which the
`len - 4` computation underflows.  Any blank line inside an indented
code block triggers it.

## Impact

Heap out-of-bounds read of unbounded length whose contents are emitted
into a publicly served page — an information disclosure of adjacent heap
(git object buffers, other rendered content, allocator metadata).
High severity, high confidence; requires only control of a rendered
markdown document, the same trust boundary as the rest of the SSR path.

## Remediation sketch

The retired renderer is replaced by the lws streaming markdown renderer,
which strips `min(4, len)` and emits the remainder as data events; the
underflow path does not exist.  Fence bodies stream directly and never
stage.

## Status history

- 2026-09-18 — filed by SA-016 continuation; fixed the same day by the
